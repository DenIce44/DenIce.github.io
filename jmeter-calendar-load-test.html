Calendar API lifecycle load test.

01 / OVERVIEW

Business behavior under load.

The workload measures complete calendar business flows rather than isolated requests. Arrival rate, target routes, input files, timeouts, and branch selection are runtime properties.

01

Open workload model

An Open Model Thread Group schedules new business-flow arrivals. Concurrency emerges from arrival rate and system response time.

02 / SCENARIO

One arrival, complete ownership.

BOTH runs the two calendar lifecycles sequentially. WORKSPACE, PERSONAL, and weighted MIXED modes reuse the same test-plan structure.

STEP 01 / AUTH→

Authenticate

Read a dedicated CSV account, sign in, extract the bearer token, and reject lifecycle traffic if token validation fails.

  • Token state reset per arrival
  • Configurable token JSONPath
  • Cookie isolation between identities

Create a unique workspace calendar, find its returned ID in the collection response, and perform asserted cleanup.

03 / RELIABILITY

Failures stay explainable.

The plan is designed to make the root HTTP failure visible while keeping deletion reachable wherever the API returned an addressable resource.

  1. 01

    Bound stalled calls

    Shared connection and response timeouts limit runaway thread accumulation in an open workload.

  2. 02

    Protect identity state

    Bearer variables and cookies are reset so authentication failures cannot leak a previous session into the next flow.

  3. 03

    Preserve cleanup after verify failure

    continue on error and sibling cleanup controllers prevent an assertion failure from short-circuiting DELETE.

  4. 04

    Reserve cleanup time

    A final zero-arrival pause starts no new work while allowing active flows to reach their final deletion request.

Operational limit: a forced JVM stop, machine failure, or Stop Test Now can still interrupt in-flight DELETE calls. Graceful completion is part of the test contract.
